# Подключение партнёра в BB

Выполни техническую настройку за пользователя, чтобы он мог начать работу с партнёром. Ему оставь подтверждение входа в браузере и, если потребуются, доверие плагину/хукам или системные права, недоступные агенту. Результат — проверенное подключение с именем аккаунта либо понятная причина остановки и одно следующее действие.

Нужны работающий агент Claude Code или Codex в BB и доступ к серверу svaib. При отсутствии методологического плагина установи его по references/native-connect.md: поручение подключить включает эту установку и штатный вход. Не требуется предварительный вход в кабинет. Этот скилл не развёртывает пространство, не меняет его документы, сервер svaib, BB, права запуска или аккаунт модели.

## Привязка и начальная проверка

Определи выбранные project/environment/host/provider через `bb status --json` и `bb thread show --self --json`; если они переданы в инструкции BB, сверь их с фактом. Работай только в этой связке. Если доступен `svaib_connect_begin`, сначала выполни серверное сопоставление по разделу ниже. В остальных режимах сначала попробуй настоящий read-only MCP-инструмент `whoami` из **текущей сессии**: успешное подключение оставь как есть.

Поручение подключить или восстановить — режим `setup`; поручение только проверить — `verify`. Если режим явно задан в инструкции BB, используй его. В `verify` не устанавливай и не меняй методологический плагин/MCP и не запускай OAuth харнеса. Отдельный вход кабинета ведёт инструмент завершения только внутри уже запущенного пользователем единого подключения. Нет инструмента или вызов не прошёл — MCP в этом разговоре не проверен. Результат другого процесса, CLI/HTTP-вызов и перечень tools эту проверку не заменяют. Если указан прежний разговор, сначала сопоставь его project/environment/host/provider с текущим; при расхождении сообщи об этом и не выдавай новую связку за проверку прежней.

В режиме `setup`, если MCP не работает, прочитай [справку по установке и входу](references/native-connect.md) — там точный источник установки, штатные команды, определение нужного профиля и браузерный вход. Выполни подготовку сам; пользователь не должен искать пути, править конфиги и копировать команды или callback. Если нужный scope установить нельзя, сообщи конкретную причину и не запускай вход в случайный профиль.

## Единое подключение из BB

Если доступен `svaib_connect_begin`, используется новое серверное сопоставление двух входов:

1. Вызови `svaib_connect_begin`. Backend сам начинает вход кабинета и открывает браузер. При `pending` повторяй тот же инструмент без повторного OAuth. `reopenBrowser:true` — только когда пользователь попросил открыть закрытую вкладку. Этот шаг ещё не проверяет native MCP.
2. В режиме setup проверь или установи методологический пакет и штатный MCP выбранного харнеса по `references/native-connect.md`. Используй вариант методологического пакета из установленного BB-плагина и подготовь его постоянный marketplace по справке. Не подменяй его пакетом из другого источника или другого харнеса. После непосредственной OAuth-команды в persistent-терминале используй `svaib_connect_wait`; после `handedOff` заверши исходный разговор. Работающий вход сохраняй. В verify не переустанавливай пакет и не запускай MCP OAuth.
3. Когда native MCP доступен, снова вызови `svaib_connect_begin` для актуального challenge. Вызови **native MCP svaib** `issue_workplace_proof`, передав ровно возвращённые `challenge` и `nonce`. Передай возвращённую строку `proof` в `svaib_connect_finish` аргументом `proof`. Receipt не разбирай и не используй как credential. Не отправляй его в Telegram, другие чаты или внешнему процессу. Backend проверяет подпись и аккаунт через собственный вход. При истечении challenge получи новый через begin без повторного OAuth.
4. Только `connected:true` завершает сопоставление двух account grants для этого запуска. Это проверка свежего обращения, а не аттестация бинарника или бессрочного входа. Затем продолжи общий account setup и онбординг; company/Screen/файлы проверяются отдельно. При разных аккаунтах сохрани рабочие входы, назови причину и спроси, какой вход человек хочет изменить. Старый whoami/CLI/text не заменяет server receipt.

Если `svaib_connect_begin` отсутствует, а инструкция BB содержит прежний unified flow (например отдельный staging), продолжай его в том же разговоре:

1. После запуска непосредственной MCP OAuth-команды в persistent-терминале вызови `svaib_connect_wait` с его `terminalId`. При `pending` повторяй тот же инструмент, без нового входа.
2. Если харнес уже подключён, а текущая сессия не видит MCP, вызови `svaib_connect_verify`. При `handedOff` проверка передана новому разговору автоматически: закончи работу в исходном, не запускай там повторный OAuth и не проси пользователя создавать чат.
3. После настоящего `whoami` вызови `svaib_connect_finish`: передай `account_id`, а при его отсутствии — `subject_id`. Backend сам открывает браузер кабинета и сверяет аккаунты. При `pending` повторяй finish без `reopenBrowser`; повторное открытие — только по просьбе пользователя. OAuth-ссылки, коды и токены в модель или терминал не переносишь.
4. Только `connected:true` завершает единое подключение. После него установочные ограничения закончились: выполняй онбординг и обычные поручения по стандартным правилам. Развёртывать каркас до завершения подключения этот скилл не поручает.

Если backend не смог получить проверяемое native-доказательство, не подменяй его текстом ответа или CLI. Повтори настоящий `whoami` один раз; если BB всё ещё не предоставляет результат с проверяемым anchor, сообщи ограничение BB и сохрани работающие входы. Повторная авторизация не исправляет отсутствие доказательства в SDK.

Для отдельной диагностики кабинета сначала установи ID вызывающего BB-плагина из origin текущего разговора/инструкции и списка установленных плагинов. Общий пакет — `svaib-workplace`, прежний отдельный — `svaib-account-prototype`; чужой статус не подставляй. Вызов `bb plugin rpc call <проверенный ID> status --json` не доказывает native MCP. Аккаунт сравнивай по `account_id`, затем прежнему `canonical_subject_id`, затем legacy `subject_id`. `tenant_id` и membership subject не являются аккаунтом. Отсутствие компании — допустимый результат регистрации; он не даёт company/Screen-права. Выбор компании для просмотра кабинета не перепривязывает рабочий чат или `.svaib/platform.json`.

## Результат

При серверном сопоставлении назови аккаунт из успешного `connected:true`: сервер проверил два входа для текущего запуска. Вне него «партнёр работает» говори только после успешного MCP `whoami` в проверяемом разговоре. Назови, где проверено; доступ ко всем источникам и работа на другом компьютере из этого не следуют. В unified flow страница получает готовность от finish; обычная отдельная проверка в разговоре эту готовность не выставляет. Готовность подключения не означает выбранную компанию, готовый Screen или развёрнутый каркас.

Вне unified flow, если внешний вход завершён, а текущая сессия ещё не видит инструмент и штатного автоматического перехода нет, подготовь короткий запрос для нового обычного разговора BB в той же среде и с тем же движком, со ссылкой на текущий. Если и свежий разговор не видит MCP, вернись к диагностике scope без повторных входов наугад. Отмена/ошибка второй стороны сохраняет уже работающее подключение.
